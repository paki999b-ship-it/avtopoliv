## Решение 7. Разбор каталога Hunter: метод и результат

**Результат:** 1224 строки, 10 семейств дождевателей, 19 страниц каталога.

| Семейство | Строк | Насадок |
|---|---|---|
| PGJ | 48 | 8 |
| PGP-ADJ | 189 | 30 |
| PGP Ultra / I-20 / PRB | 197 | 30 |
| I-25 | 140 | 20 |
| I-40 | 147 | 19 |

### Правило интенсивности из §8 п.1 подтверждено данными каталога

ТЗ утверждает: «интенсивность полива в каталоге приводится для сектора 180°,
для 360° делить на 2». Проверка на самих данных показала, что каталожная
интенсивность точно воспроизводится формулой

```
PR□ = q · (360 / сектор) / R²        PR△ = PR□ / 0,866
```

при шаге «радиус в радиус» (S = R). В таблицах MP Rotator и форсунок Pro, где
колонка сектора есть, формула сходится с указанным в ней сектором. В таблицах
роторов, где колонки сектора нет, она сходится при секторе 180° — это и есть
правило ТЗ.

Расчётный движок воспроизводит каталожные значения **без каких-либо поправок**:
`headPrecipitationRate({ flowLph, spacingM: radius, sectorDeg: 180 })` даёт те
же числа. Это закреплено тестом «Сверка §5.6 с каталогом Hunter Vol. 41 (RU)»
в `packages/core/src/agronomy/agronomy.test.ts`.

**Исключение, найденное в данных:** базовый сектор различается не по странице,
а по блоку. На стр. 33 (двойные противонаправленные насадки I-40) и во втором
блоке стр. 37 (I-90-36V) интенсивность приведена для 360°: там формула сходится
только при этом секторе. Задаётся полем `assumedSectorDeg` в описании страницы.

### Сверка вместо выборочного просмотра

§8 п.1 ТЗ требует сверить «минимум по 3 строки на каждую модель». Сделано
и это, и больше:

1. **Сплошная арифметическая сверка.** Каждая строка содержит пять напечатанных
   чисел: радиус, расход в м³/ч, расход в л/мин и две интенсивности. Они связаны
   формулой выше, поэтому расход проверяется против интенсивностей. Строка
   засчитывается, только если хотя бы одна колонка расхода сходится с **обеими**
   интенсивностями — три независимых печатных числа против двух, случайным такое
   совпадение не бывает.
   **Результат: 1203 строки из 1206 (99,8 %).**
2. **Выборочная сверка по 3 строки на каждую модель** — 30 строк,
   `npm run verify:catalog` → `content/reference/hunter-nozzles-spotcheck.md`.
   В отчёте рядом с разобранной записью печатается сырая строка текстового слоя
   PDF, так что разбор проверяется посимвольно. Все 30 сходятся.

### Почему нельзя доверять одной колонке расхода

Каталог печатает расход дважды — в м³/ч и в л/мин, — и **ни одна из колонок не
надёжна сама по себе**:

- у м³/ч два знака после запятой: для мелких форсунок 0,04 м³/ч — это ±12 %
  неопределённости, и сверка по ней даёт ложные расхождения;
- на стр. 27 текстовый слой PDF отдаёт искажённые значения в колонке л/мин;
- на стр. 29 в колонке м³/ч «3,08» читается как «30,8» — расход в десять раз
  больше физически возможного для этой насадки.

Поэтому строка проверяется по обеим колонкам, в выгрузку идёт сошедшаяся, а
какая именно — записано в поле `flowSource`. Одиннадцать строк восстановлены
таким образом; у каждой в поле `issue` отмечено, какая колонка была повреждена.

### Три строки не прошли сверку — в приложение не идут

| Стр. | Насадка | Каталог PR□/PR△ | Расчёт |
|---|---|---|---|
| 32 | I-40, высокоскоростная 10 светло-зелёная, 3 бар | 34 / 28 | 24,5 / 28,3 |
| 32 | I-40, высокоскоростная 15 серая, 6 бар | 32 / 39 | 31,9 / 36,9 |
| 77 | Форсунки Pro с фиксированным сектором, радиус 1,5 м, 180°, 2,1 бар | 49 / 57 | 46,4 / 53,6 |

Первая — очевидный сбой текстового слоя: интенсивность треугольной раскладки
физически не может быть **меньше** квадратной, а «28» при этом точно совпадает
с расчётом — значит, повреждено именно «34» (должно быть 24). Две другие —
пограничные расхождения в 6–7 %, вероятно от округления радиуса в каталоге.

Все три помечены `verified: false`. **Требование к UI: строки с
`verified: false` в справочник не выводятся либо выводятся с явной пометкой
«требует сверки с печатным каталогом».**

## Решение 1. Стек: `node:sqlite` вместо `better-sqlite3`

**Дата:** 2026-08-28

На рабочей машине активна политика Windows Application Control, которая
блокирует загрузку любых нативных модулей `.node`:

```
Error: An Application Control policy has blocked this file.
\\?\...\node_modules\@rollup\rollup-win32-x64-msvc\rollup.win32-x64-msvc.node
code: 'ERR_DLOPEN_FAILED'
```

Проверено: `better-sqlite3` — нативный аддон, он будет заблокирован так же.
Встроенный в бинарник Node модуль `node:sqlite` работает (проверено на
Node 24.18): отдельного `.node` файла у него нет, политике блокировать нечего.

**Решение:** использовать `node:sqlite` (`DatabaseSync`) вместо
`better-sqlite3`. API синхронный и близкий по духу, миграция при
необходимости обратно — механическая.

**Отклонение от §2 ТЗ:** да, там прямо назван `better-sqlite3`. Отклонение
вынужденное: с ним приложение на этой машине не запустится вообще.

**Что проверить перед релизом:** доступен ли `node:sqlite` в той версии
Node, которую бандлит выбранная версия Electron. Если нет — запасной вариант
`sql.js` (WASM, тоже без нативных аддонов).
**Закрыто 2026-08-29:** Electron 44 несёт Node 24.18.1, модуль доступен без
флага — см. решение 9.

## Решение 4. Метрическая формула продувки в §5.15 исправлена

**Дата:** 2026-08-28

§5.15 ТЗ приводит два правила:

```
CFM ≈ (расход зоны в GPM) / 7,5
м³/мин ≈ (расход зоны в л/мин) / 283
```

Они не согласуются между собой. Проверка цепочки:

```
GPM  = л/мин / 3,7854
CFM  = GPM / 7,5
1 CFM = 0,0283168 м³/мин
→ м³/мин = л/мин · 0,0283168 / (3,7854 · 7,5) = л/мин / 1002,6
```

Число 283 — это множитель 0,0283, попавший в знаменатель без пересчёта:
метрический вариант из ТЗ завышает требуемую производительность компрессора
примерно в 3,5 раза.

**Решение:** реализован согласованный вариант **м³/мин ≈ (л/мин) / 1000**.
Точный делитель вынесен в константу `BLOWOUT_LPM_TO_M3MIN_DIVISOR`, тест
проверяет, что CFM и м³/мин описывают одну и ту же производительность.
Расхождение с ТЗ прокомментировано прямо в шапке `src/ops/blowout.ts`.

## Решение 5. Буферная ёмкость считается в двух вариантах

**Дата:** 2026-08-28

В §5.10 формула доступного объёма содержит запас 0,8, а формула объёма
ёмкости — нет:

```
Доступно = Дебит · Окно · 1000 · 0,8
V_ёмкости ≥ Потребность − Дебит · Окно
```

Из-за этого возможен разрыв: баланс уже не сходится, а требуемая ёмкость
формально равна нулю.

**Решение:** калькулятор возвращает оба значения — `tankVolumeStrictL`
(буквально по ТЗ) и `tankVolumeWithReserveL` (с тем же запасом 0,8).
К проектированию рекомендуется второй, в UI он выводится основным.

§8 п.1 ТЗ: «интенсивность полива в каталоге приводится для сектора 180°.

## Решение 8. Недостающие справочные данные собраны из открытых источников

**Дата:** 2026-08-29

Справочник «ИрригоЭксперт» и Handbook of Applied Hydrology так и не переданы,
поэтому таблицы труб и почв нельзя было закрыть по §8 ТЗ. Вместо ожидания
недостающих файлов данные подтверждены по первоисточникам в интернете. Материал
перенесён в контент при сборке — офлайн-требование ТЗ §1 не нарушается, сеть
нужна только разработчику.

### Трубы — статус `verified`

| Материал | Источник | Результат |
|---|---|---|
| ПЭ100 SDR11 и SDR17 | ГОСТ 18599-2001, таблица 4 | все 23 строки совпали построчно |
| ПВХ SDR21 и SDR13,6 | ISO 1452-2:2009, Table 2 | все 15 строк совпали построчно |

**Снято подозрение по ПЭ100 SDR11 Ø75.** Юнит-тест помечал строку как
сомнительную: толщина 6,8 мм при расчётном D/SDR = 6,818 мм. Таблица 4 ГОСТ
18599-2001 подтверждает именно 6,8 мм — ряд толщин ISO 4065 округлён и не
выводится из D/SDR арифметически. Инвариант оставлен с допуском 0,05 мм вниз.

**Уточнена привязка PN к SDR для ПВХ.** ISO 1452-2 задаёт её через коэффициент
запаса: при C = 2,5 (для труб свыше 90 мм) SDR 21 = PN10 и SDR 13,6 = PN16;
при C = 2,0 те же серии маркируются PN12,5 и PN20. Приняты значения при C = 2,5,
то есть маркировка консервативная — заявленное давление ниже, чем при C = 2,0.

### Почвы — статус `verified` (кроме торфа)

- **Впитывание:** FAO, Irrigation Water Management Training Manual, «Irrigation
  Methods», Annex 2, Table 7.
- **Доступная влага:** UC ANR, Center for Landscape & Urban Horticulture,
  «Soil Water Holding Characteristics» (дюймы воды на фут, пересчёт
  1 in/ft = 83,33 мм/м), подтверждено публикацией UC ANR 80223, Appendix E.

Значения заметно изменились по сравнению с принятыми ранее «типовыми»: у
суглинка среднего впитывание 10–20 вместо 8–15 мм/ч, влагоёмкость 125–192 вместо
140–190 мм/м, у глины 133–208 вместо 180–230 мм/м. Сквозной интеграционный тест
поймал сдвиг и обновлён: на суглинке роторам с PR 12 мм/ч режим cycle & soak
теперь не нужен (впитывание 15 мм/ч), спреям с PR 35 мм/ч — нужен.

Торф оставлен со статусом `to_verify`: органических грунтов нет ни в таблице
FAO, ни у UC ANR.

### Найденная ошибка в источнике FAO

Table 7 печатает для песка «less than 30 mm/hour» (сверено дословно). Это
противоречит порядку самой таблицы: супесь в ней получает 20–30 мм/ч, а песок
не может впитывать медленнее супеси. Приложение читает строку как «более 30» и
использует 30–50 мм/ч.

Добавлен юнит-тест, проверяющий монотонность ряда впитывания от песка к глине —
именно это свойство нарушала исходная строка. Сама история пойдёт в урок как
пример: проверять на здравый смысл нужно даже документ FAO.

### Добавлено в расчётный движок

Поправка допустимого истощения на водопотребление из FAO-56, глава 8:

```
p = p_табл + 0,04 · (5 − ETc),   0,1 ≤ p ≤ 0,8,   ETc в мм/сут
```

В жару растение расходует запас быстрее, чем корни успевают его добирать, —
поливать надо раньше. Реализовано в `soilWaterHoldingNorm` как необязательный
вход `etcMmDay`; без него MAD берётся как раньше.

MAD 0,5 для декоративного ландшафта подтверждён дословно публикацией UC ANR
80223: «For many landscape plants, this allowable soil moisture depletion is
about 50 percent of the available soil moisture».

Множитель графика SM = 1/DU и порог приемлемости DU_lq ≥ 0,70 подтверждены
материалами Irrigation Association и UC ANR — реализация §5.7 совпала с
отраслевой методикой без изменений.

- внутренний диаметр трубы = наружный минус две толщины стенки;
- номинальная толщина стенки согласуется с расчётной `D/SDR`
  (допуск: 0,05 мм вниз на округление ряда стандарта, 0,5 мм вверх);
- у каждой строки непустое поле `source`;
- диапазоны почв непротиворечивы (min ≤ max), песок впитывает быстрее глины,
  глина держит больше влаги;
- Kc газона выше Kc кустарников, глубина корней растёт от газона к деревьям.

**Отдельная строка к сверке:** ПЭ100 SDR11 Ø75 указан с толщиной стенки
6,8 мм, тогда как `D/SDR` = 6,818 мм. Ряд толщин ISO 4065 округлён и не
выводится из `D/SDR` арифметически, поэтому значение оставлено как есть,
но требует сверки с печатным сортаментом.

## Инженерные решения расчётного движка

**Единая форма результата.** Каждая расчётная функция возвращает
`CalcResult<T>`: `values` (числа), `steps` (формула → подстановка →
результат) и `notes` (замечания «что не так → почему → как исправить»).
Требование §3.2 «показывать формулу, подстановку чисел и результат»
выполняется движком, а не вёрсткой, — UI не может его случайно потерять.

**Потери в капельной линии** считаются с поправкой Кристиансена
`F = 1/(m+1) + 1/(2N) + √(m−1)/(6N²)` при `m = 1,852`: расход по линии
убывает с каждой капельницей, и считать потери по полному расходу на всю
длину было бы завышением втрое.

**Зависимость расхода капельницы от давления** принята степенной,
`q ~ h^x`, `x = 0,5` по умолчанию (турбулентный лабиринт). Показатель
вынесен во входной параметр: у конкретных изделий он берётся из паспорта.

**Кривая насоса** аппроксимируется параболой `H = a + b·Q + c·Q²` по 2–3
точкам, введённым пользователем (по двум точкам `b = 0`). Характеристика
системы — `H = H_ст + k·Q^1,852`, в форме Хазена–Вильямса. Рабочая точка
ищется делением отрезка пополам. Кривых конкретных насосов в приложении нет
и не будет — это прямо требование §5.11 и §8 ТЗ.

**Округление.** Промежуточные величины, которые идут дальше по цепочке
расчёта (норма полива, интервал, запас влаги), хранятся с двумя знаками:
округление до одного знака давало заметное расхождение в сквозном примере.

**Максимальная длина кабеля** округляется вниз, а не арифметически:
округление вверх выдавало длину, на которой допуск 2,4 В уже нарушен.

**Предельное давление продувки** на уровне системы берётся по материалу
трубопровода, а более жёсткие ограничения по типу дождевателя (спреи,
капельные зоны) применяются к каждой зоне отдельно.

## Решение 15. Формы калькуляторов описываются данными, а не вёрсткой

**Дата:** 2026-08-29

Шестнадцать калькуляторов §5 отличаются набором полей, а не поведением.
Поэтому каждый описан объектом `CalcDefinition` (поля, значения по умолчанию,
вызов функции движка, выводимые величины, таблицы, текст «Пояснить»), а рисует
их всех один исполнитель `CalcRunner`.

Что это даёт: требование §3.2 показывать формулу, подстановку и результат
выполняется в одном месте, и «забыть» его в отдельно взятом калькуляторе
невозможно. Тест проверяет, что у каждого расчёта из реестра движка есть форма,
что она считается на значениях по умолчанию и что каждое выводимое поле
действительно существует в результате движка.

**Формул в этом слое нет.** Описание только сопоставляет поля формы аргументам
функции из `@irrigo/core` — §2 ТЗ прямо запрещает дублировать формулы в UI.

**Описания свободны от React.** Вставка своего блока под результатом (график
кривой насоса) задаётся ключом `extraKey`, а не компонентом: иначе тесты
описаний тянули бы за собой recharts и DOM.

## Решение 16. Имперская система — в представлении, расчёт всегда в метрике

**Дата:** 2026-08-29

§13 ТЗ требует, чтобы переключение единиц применялось во всех калькуляторах.
Реализовано так: движок принимает и возвращает только метрику, а поля формы
объявляют физическую величину (`quantity`). Значение переводится при вводе в
форму и обратно перед вызовом движка; подписи единиц подменяются там же.

**Вывод формулы (`steps`) не переводится и остаётся метрическим.** Формулы §5
определены в СИ; подстановка, пересчитанная в дюймы и галлоны, перестала бы
сходиться с формулой, напечатанной строкой выше, и стала бы вредной. При
имперской системе над формой стоит пояснение об этом, а блок «Как это
посчитано» помечен значком «метрические единицы».

Обратимость перевода закреплена тестом: значение, переведённое в имперские
единицы и обратно, совпадает с исходным по всем десяти величинам.

## Решение 21. Клапаны: опорной принята таблица «в кПа», расхождения каталога показаны

**Дата:** 2026-08-29

длиннее уже нарушен.

**Ток взят 0,37 А на клапан** — пусковой ток стандартного электромагнита 24 В
при 50 Гц по каталогу Hunter (стр. 87, 88, 90). В сети 60 Гц он ниже (0,35 А),
но здесь сеть 50 Гц, и брать меньшее значение было бы занижением.

## Решение 26. Урок — список типизированных блоков, а не строка markdown

**Дата:** 2026-08-29

§1 ТЗ требует три уровня подачи одного и того же материала: владелец участка,
монтажник, проектировщик. Писать три версии каждого урока — это втрое больше
текста и три источника расхождений при любой правке.

Поэтому урок хранится списком блоков (`blocks_json`), у каждого из которых
есть поле `audience`. Общий текст читают все; вывод формулы помечен
`designer`, практические указания на объекте — `installer`. Переключатель в
профиле показывает или прячет блок целиком, а текст остаётся один.

Типы блоков: текст, заголовок, список, врезка (заметка / внимание / опасно /
как надо), формула с подстановкой, таблица, ссылка на калькулятор, ссылка на
справочник, схема. Каждый рисуется своим компонентом, поэтому «сломать
вёрстку урока» опечаткой в контенте нельзя.

**Markdown не разбирается.** Внутри текста работают только `**жирный**`,
`` `моноширинный` `` и `[[термин]]` — ссылка на глоссарий, требуемая §3.3.8
(«термины в уроках подсвечиваются и раскрываются по клику»). Разбор — сорок
строк своего кода вместо трёх зависимостей и чужих неожиданностей.

В поле `body_md` при сборке кладётся плоский текст урока: он нужен поисковому
индексу, которому блоки ни к чему.

## Решение 28. XP за урок начисляется один раз

**Дата:** 2026-08-29

Мини-тест можно перепроходить сколько угодно: это нормальный способ разобрать
ошибки. Но XP даётся только при первом зачёте — иначе пересдача превращается в
способ накручивать опыт, а прогресс перестаёт что-либо значить.

Проходной балл мини-теста — 70 %. Урок при этом помечается пройденным, а дата
прохождения не переписывается при повторных попытках (`COALESCE` на
`completed_at`): интересна первая, а не последняя.

Порядок завершения теста тот же, что §3.9 требует от экзамена: посчитать →
сохранить → показать результат, всё в одной транзакции. Попытка и ответы либо
записываются вместе, либо не записываются вовсе.

**Правильные ответы в renderer не приходят вовсе.** `academy:quiz` отдаёт
вопросы без поля `correct`, проверка целиком в главном процессе. Тест это
проверяет буквально — сериализует вопрос и ищет в нём слово «correct».

## Решение 33. Покрытие участка считается выборкой по сетке

**Дата:** 2026-08-29

§3.4 требует показывать площадь непокрытых зон и площадь перекрытия. Это
площадь многоугольника за вычетом объединения десятков круговых секторов,
часть которых пересекается по три и по четыре. Аналитически такое считается
булевыми операциями над кривыми: много кода, много вырожденных случаев и
никакой пользы для нужной здесь точности.

Принята выборка по сетке: участок покрывается ячейками, центр каждой
проверяется на попадание в контур, в препятствия и в секторы голов. Один
проход даёт сразу всё — покрытие, перекрытие, непокрытую площадь, полив мимо
цели и координаты сухих пятен, которые §3.4 требует показывать красным.

**Точность проверяется сходимостью с аналитикой.** Тесты сверяют результат с
площадью круга и четверти круга: при ячейке 0,2 м расхождение меньше 3 %.
Отдельный тест требует, чтобы мельче сетка давала меньшую ошибку — иначе
метод был бы не приближением, а произволом.

Сетка расширена на радиус самой дальнобойной головы: только так виден полив
за границу участка. Число ячеек ограничено сверху, при превышении шаг
удваивается — лучше посчитать грубее, чем повесить интерфейс.

Непокрытые ячейки склеиваются в пятна по восьми направлениям: пользователю
нужно «три сухих пятна по 2 м²», а не «сорок восемь непокрытых ячеек».

## Решение 34. Проверка шага привязана к измеренному покрытию

**Дата:** 2026-08-29

Изначально замечание «шаг больше радиуса» выдавалось всегда, когда отношение
среднего шага к среднему радиусу превышало 1,15. Тест на заведомо хорошей
раскладке это поймал: четыре угловые головы с радиусом 9 м на участке 12×12

Правило «шаг равен радиусу» — способ добиться сплошного покрытия, а не цель
сама по себе. Покрытие здесь измеряется напрямую, поэтому широкий шаг теперь
отмечается только тогда, когда он действительно оставил сухие места. Иначе
замечание дублировало бы измерение и придиралось к работающей раскладке.

**Побочная находка тех же тестов:** угловая голова с сектором ровно 90°,
отставленная от кромки, физически не покрывает полосу за собой — сектор
смотрит внутрь участка. Это не дефект движка, а свойство геометрии, которое
на объекте решают тем, что ставят голову вплотную к углу и раскрывают сектор
чуть шире 90°. Эталонные раскладки в тестах исправлены на реалистичные.

## Решение 35. Замечания раскладки — те же `CalcNote`, что у калькуляторов

**Дата:** 2026-08-29

Тренажёр выдаёт замечания в той же структуре, что и расчётный движок: что не
так → почему → как исправить, плюс ключ урока. Три следствия:

- UI показывает их тем же компонентом, что и замечания калькуляторов;
- у каждого замечания обязателен урок, куда оно ведёт, — это проверяется тестом;
- сравнение с эталоном сводится к разнице множеств кодов замечаний.

Сравнение с эталоном (§3.4) отдаёт только те замечания, которых у эталона нет:
если эталонное решение тоже не покрывает угол за домом, ставить это в вину
ученику неправильно. Вердикт «лучше / сопоставимо / хуже» имеет полосу
нечувствительности 0,05, чтобы разница в одну ячейку сетки не объявлялась
победой.

## Решение 36. Эталоны заданий генерируются и проверяются, а не пишутся руками

**Дата:** 2026-08-30

§13 ТЗ требует `qa_verified = true` у каждого задания тренажёра. Проставить
это поле руками — значит объявить решение проверенным, не проверив.

Задания собирает `scripts/build-layout-tasks.ts`: он генерирует эталонную
раскладку по сетке, подбирает сектор каждой головы по форме участка и тут же
прогоняет результат через расчётный движок. Задание попадает в выгрузку,
только если эталон действительно проходит проверки §3.4; при провале скрипт
падает. Результат проверки — покрытие, оценка, число голов, расход, перелив —
пишется в `qaNotes` и показывается пользователю в разборе. Наполнение базы
дополнительно отказывается принимать задание с `qaVerified: false`.

**Подбор сектора.** Направления перебираются по кругу с шагом в градус;
направление считается рабочим, если на половине радиуса в нём есть поливаемая
площадь. Берётся самая длинная непрерывная дуга — так угловая голова получает
четверть круга, краевая половину, внутренняя полный круг, и это работает на
любом контуре, включая L-образный и треугольный.

Расход каждой головы считается пропорционально сектору — это и есть
согласованная интенсивность §5.6, и по ней же есть отдельный тест.

## Решение 37. Полив за забор и полив по своей дорожке — разные замечания

**Дата:** 2026-08-30

Изначально перелив считался одним числом с порогом 15 % от поливаемой площади.
Сборка заданий на этом провалилась почти вся, и разбор показал, что порог
смешивает две несравнимые вещи.

Полив за границу участка неустраним частично: круглый факел не вписывается в
прямой угол, а на полосе шириной 3 м радиус заведомо больше её ширины. Полив
по собственной дорожке или террасе — всегда дефект: мокрая плитка скользит и
зеленеет, зимой на ней лёд.

Теперь это два замечания с разными шкалами:

- за границу — доля от поливаемой площади: выше 25 % предупреждение, выше 40 %
  ошибка;
- по препятствиям — **доля самого препятствия**, а не участка. Иначе мокрая
  насквозь дорожка на большом газоне выглядела бы мелочью, а пара брызг на
  угол дома — проблемой. Выше 40 % предупреждение, выше 75 % ошибка.

**Побочный вывод для контента.** Дорожка посреди газона мокнет при любой
раскладке: соседние головы перекрывают её с обеих сторон. Учебное задание
переделано на дорожку вдоль края, где сектор действительно можно отвернуть, —
задача, которая имеет решение.

## Решение 38. Шкала оценки привязана к порогам замечаний

**Дата:** 2026-08-30

обнуляла балл за перелив уже при 20 %, тогда как предупреждение выдаётся с

эталон обязан набирать проходной балл, иначе ученику нечего превзойти.

## Решение 39. Оценку раскладки пересчитывает главный процесс

**Дата:** 2026-08-30

Интерфейс считает покрытие и замечания вживую — иначе тренажёр не был бы
тренажёром. Но в прогресс идёт только то, что пересчитал главный процесс тем
же движком: присланное значение не принимается вовсе. Разница между ними

стороне главного процесса: попытка одного профиля не открывает эталон другому.

## Решение 40. Сценарии «Найди ошибку» — карточки фактов, а не 30 иллюстраций

§3.5 требует «описание объекта + схема/фото-подобная иллюстрация + 3–6 скрытых
ошибок». Тридцать содержательных схем — это тридцать рисунков, каждый из
которых сам может врать; проверить их нечем, а нарисовать «фото-подобно»
средствами SVG невозможно.

Вместо этого сценарий состоит из описания объекта и набора **карточек-фактов**
о нём, сгруппированных по узлам («Расход», «Кабель», «Продувка»). Часть фактов
описывает ошибку, часть — верно выполненный узел; пользователь отмечает ошибки.

Что это даёт по сравнению с рисунком: ошибку можно сформулировать точно
(«кабель 0,5 мм² на 160 м», а не «что-то не так с проводкой»), к каждой
карточке привязать разбор, урок и калькулятор, и проверить содержимое тестом.
Поле `image_path` в схеме сохранено — иллюстрации можно добавить позже, не
меняя ни модель данных, ни логику проверки.

## Решение 41. Ложное срабатывание весит столько же, сколько находка

Оценка сценария:

```
оценка = max(0, (найдено − отмечено напрасно) / всего ошибок)
```

Две отвергнутые альтернативы:

- **не штрафовать лишние отметки** — выигрышной стратегией становится
  «отметить всё», и тренажёр перестаёт чему-либо учить;
- **считать долю верных решений по всем карточкам** — сценарий из шести
  карточек с двумя ошибками даёт 67 % за полное бездействие.

Штраф ровно того же веса делает угадывание бессмысленным: матожидание
случайной отметки — ноль. Правило объявляется пользователю до начала:
скрытый штраф читался бы как ошибка программы.

Проходной балл 0,75 — тот же, что зашит в `sectionProgress` для раздела
`errors`; тест сверяет эти два числа, чтобы они не разъехались.

## Решение 44. Дерево диагностики хранится плоско, а отдаётся целиком

Схема §7 описывает `diagnostics_nodes` как плоскую таблицу со ссылкой на
родителя — так и наполняется. В контенте (`content/diagnostics/*.json`) то же

одной строкой `conclusion` они не описываются), `hint` (описание симптома в
списке) и `order_index`.

## Решение 47. Исход без урока не собирается

§3.6 требует, чтобы каждый исход был связан с уроком. Это проверка при
сборке, а не пожелание: `seed-diagnostics.ts` отказывается писать исход, у

написан — и пользователь упёрся бы в пустой экран.

По той же причине диагностика наполняется после Академии: ссылка проверяется
по уже заполненной таблице.

Заодно проверяется, что причины идут по убыванию вероятности, что у исхода
есть и замер, и действие, и что каждая ветка заканчивается исходом, а не
вопросом.

нормально.

## Решение 50. Обязательные формулировки проверяются тестом

Тесты раздела проверяют не только структуру, но и наличие конкретных
формулировок, которых требуют §3.8 и §10: «квалифицированный электрик» и
«не является допуском», все пять устройств защиты от обратного потока вместе
с высотой установки и отсылкой к местным правилам и водоканалу, запрет отбора
выше дебита, пределы давления при продувке 3,5 и 5,5 бар, «не заменяет
инструктаж по охране труда» в первой помощи.

Формулировка — это и есть содержание такого раздела. Правка текста, из
которой пропала граница ответственности, должна ронять сборку, а не проходить
незамеченной.

**Ловушка при написании тестов:** `\w` в JavaScript — это латиница с цифрами,
кириллицу он не покрывает. Шаблон вида `/квалифицированн\w+ электрик/` молча
не совпадает. В тестах раздела стоит явный класс `[а-яё]`.

## Решение 51. Тема отмечается прочитанной по открытию

В отличие от урока с мини-тестом и сценария с проверкой, у карточки
безопасности нет упражнения. Требовать отдельного нажатия «прочитано» ради
галочки в прогрессе незачем: пользователь пришёл прочитать — он прочитал.

Это осознанно слабее, чем в остальных разделах, и такое различие уместно:
раздел существует, чтобы его прочли, а не чтобы его сдали.

## Решение 52. Расчётные вопросы генерируются движком, а не пишутся руками

`scripts/build-question-bank.ts` описывает каждый расчётный вопрос условием и
вызовом функции `@irrigo/core`; правильный ответ и подстановка в пояснении —
результат расчёта, а не набранное число.

Причина в §0 п.6 ТЗ: ни одна цифра не берётся «по памяти». Написанный руками
ответ создаёт класс ошибок, который иначе неизбежен: условие подправили, число
пересчитать забыли — и учебная программа учит неверному. Заодно ответ считает
ровно тот же движок, которым потом проверяется ответ пользователя.

Файл `content/questions/bank-numeric.json` помечен как генерируемый: править
его руками нельзя, правки затрёт следующая сборка. Команда — `npm run
build:questions`.

При сборке скрипт поймал три несоответствия сигнатурам движка (имена
материалов труб, поля входа `waterHammer` и `waterBalance`), то есть сработал
как проверка совместимости контента с движком.

## Решение 55. Порядок завершения экзамена выражен в коде, а не в комментарии

§3.9 предупреждает о ловушке: результат теряется, если состояние сбросить до
записи. Решение прямое — `exam:submit` делает расчёт и сохранение одной
операцией в одной транзакции и возвращает уже сохранённый результат. Пока он
не вернулся, интерфейсу некуда переходить; ответы из состояния при этом не
стираются, так что при ошибке записи работа не потеряна.

Тест проверяет не порядок вызовов, а факт: то, что вернула функция, уже лежит
в `exam_results` — сверяются балл, число верных и признак сдачи.

Номер сертификата проставляется в той же транзакции, сразу после вставки:
он зависит от идентификатора попытки, поэтому раньше его знать нельзя.

## Решение 58. Интенсивность полосовой форсунки считается, а не переписывается

В `STRIP_NOZZLES` хранятся только измеренные производителем величины:
давление, ширина и длина полосы, расход. Интенсивность вычисляет
`stripNozzlePrecipitationRate` по §5.6 — и при наполнении базы, и в карточке
справочника, и в калькуляторе. Одно число получается одним способом.

Заодно при наполнении проверяется внутренняя согласованность листа: расход
дан и в м³/ч, и в л/мин, и эти две формы должны сходиться в пределах
округления (0,11 л/мин). Расхождение больше — опечатка при переносе, и сборка
падает.

Контрольный пример в тестах: SS-530 при 2,1 бар — 300 л/ч на полосу
1,5 × 9,1 м = 13,65 м² → 22 мм/ч.

## Решение 59. Полоса — это не сектор, и формула у неё другая

Стандартный расчёт PR идёт через площадь, приходящуюся на голову в сетке
раскладки, с поправкой на сектор. К полосовой форсунке он неприменим: она
поливает прямоугольник фиксированного размера, и шаг раскладки в расчёт не
входит вовсе — площадь берётся прямо из технического листа.

Отсюда следствие, которое движок выдаёт замечанием при каждом расчёте:
полосовые не согласуются по интенсивности с веерными и роторными соплами,
и в одной зоне с ними не ставятся (§11 п.2 ТЗ — тот же случай, что «роторы со
спреями»). Между собой полосовые сочетаются: у семейства одинаковый расход на
метр полосы, поэтому угловые, боковые и центральная модели дают согласованную
интенсивность. Расход на метр показан в результатах калькулятора отдельной
строкой — именно по нему это и проверяется.

## Решение 61. Из четырёх каталогов насосов машинно читается один

В `/content` лежат четыре PDF с насосами. Устроены они по-разному, и это

| Файл | Что внутри | Итог |
|---|---|---|
| `SPERONI-cat-2026.pdf` | Рабочие характеристики напечатаны **таблицей**: строка «m3/h» задаёт расходы, строка модели под ней — напор в каждой точке | **319 моделей** извлечено |

| `databooklet-cr-91830035-0222.pdf` (Grundfos CR) | То же | пропущен |
| `LEO Industrial Pumps.pdf` | Скан: текстового слоя нет ни на одной из 366 страниц | пропущен |

**Почему кривые Grundfos не оцифрованы.** Проверка операторов страницы
показала около 900 отдельных штрихов: сетка, засечки, три наложенных графика
(H, P2, NPSH/КПД) с общей осью расхода и семейство из пяти кривых на одном
поле. Отделить кривую от сетки и, главное, привязать каждую из пяти к своей
модели можно только по мелким подписям у линий — то есть на глаз, по одной
модели за раз. Ошибка в такой привязке не заметна: получится правдоподобная
кривая не от того насоса. Это ровно то, что задача запрещает, поэтому
Grundfos в подбор не попал.

**Почему LEO не распознан.** Распознавание текста потребовало бы внешнего
пакета, которого в проекте нет, а приложение обязано собираться и работать
офлайн без новых зависимостей (§13 ТЗ).

Пропуск не спрятан: причина по каждому файлу сохраняется в `app_meta` и
показывается в калькуляторе под списком подобранных насосов. Пользователь
видит, каких каталогов в подборе нет и почему, — иначе отсутствие Grundfos
читалось бы как «таких насосов не бывает».

## Решение 62. Каталожная кривая — ломаная, а не аппроксимация

В движке уже была `fitPumpCurve`: она подгоняет параболу под две-три точки,
которые пользователь берёт из паспорта своего насоса. Для каталожного насоса
такой подход не годится: точек шесть-шестнадцать, они сняты с напечатанной
таблицы, и парабола между ними «дорисовала» бы напор, которого производитель
не публиковал.

Поэтому добавлен отдельный модуль `packages/core/src/pump/catalog.ts`:
`catalogHeadAt` читает кривую как ломаную с линейной интерполяцией, а за
пределами таблицы возвращает `null` — экстраполяция паспортной кривой это
выдумывание характеристики. График рисует ту же ломаную (`type="linear"`),
поэтому картинка и число всегда совпадают.

Обе функции остались: первая отвечает на вопрос «что будет с моим насосом»,
вторая — «какой насос взять».

## Решение 63. Запас по напору ограничен сверху, а не только снизу

Подходящим считается насос, у которого напор в требуемой точке расхода не
ниже требуемого **и не выше требуемого более чем на 30 %**.

Верхняя граница здесь так же важна, как нижняя. Насос с двукратным запасом не
надёжнее: он работает левее своей эффективной зоны, греется и гонит давление,
которое всё равно придётся срезать редуктором. Это тот же принцип «запас без
избыточности», по которому подбирается диаметр трубы.

Сортировка — по возрастанию запаса: первым идёт насос с минимальным
оправданным превышением.

## Решение 64. Ошибки разбора PDF ловятся свойствами кривой, а не глазами

Табличный разбор по координатам ошибается предсказуемо: в столбцы расхода
попадает строка из соседней таблицы — габаритной или строка единиц «lt/1'».
Отличить такую строку от модели можно по физике:

- **кривая насоса не возрастает** — напор падает с расходом всегда;
- напор бытового и промышленного насоса лежит в пределах до 500 м;
- мощность — от 0,1 до 500 кВт.

Эти три проверки стоят и в скрипте извлечения, и в наполнении базы, и в
тестах. На первом прогоне они отсеяли 100 ложных строк из 425, включая записи
с «мощностью» 525 кВт, снятой из габаритной таблицы.

Отдельно чинились два дефекта разбора, которые проверки бы не поймали:

1. **Склеенные числа.** PDF нередко ставит несколько соседних ячеек одним
   текстовым объектом («32,7 32,5 32,3»). Пока разбор брал только «чисто
   числовые» элементы, у половины моделей терялась половина точек кривой:
   CSM 40-160 B получал 6 точек вместо 12. Теперь элемент разворачивается в
   список чисел, а первое привязывается к ближайшему столбцу расхода.
2. **Мощность там, где её нет.** У мелких дренажных насосов в таблице стоят
   ватты и ёмкость конденсатора, а колонки «kW» нет вовсе. Разбор брал первое
   попавшееся число и выдавал 1,6 кВт вместо 300 Вт. Теперь мощность
   заполняется, только если в шапке есть колонка «kW»; иначе — пусто и
   пометка «уточнить по каталогу».

## Решение 65. Тема — атрибут на корне, значения — те же имена токенов

Механизма переключения тем в проекте не было: палитра лежала одна, в `:root`.
Второй набор значений добавлен под `:root[data-theme='light']`, а renderer
ставит атрибут по настройке профиля. Имена токенов при перекраске не менялись
— они встречаются в сотнях мест по коду, и переименование ради смены цвета
сломало бы всё разом.

Тема хранится в профиле, рядом с системой единиц и уровнем подачи (миграция
V8): за одним компьютером работают несколько человек, и тема у каждого своя.
Выбирается она при этом в разделе «Настройки приложения», а не среди учебных
настроек профиля — пользователь ищет её там.

## Решение 66. Hover кнопки и акцентный текст разведены на разные токены

`accent-strong` служил сразу двум ролям: цветом наведения на акцентную кнопку
(`hover:bg-accent-strong`) и цветом акцентного текста (`text-accent-strong`,
10 мест). В одной теме это сходило с рук, в двух — нет:

- наведение в тёмной теме **светлее** акцента, а в светлой должно быть
  **темнее** его;
- светлый акцент светлой темы (#6FA98A) как текст на белом даёт около 2,5:1 —
  нечитаемо.

Поэтому добавлены два токена: `--iw-accent-hover` для наведения и
`--iw-accent-ink` для текста. Это добавление, а не переименование: старые
имена остались на своих ролях.

## Решение 67. Синий «информация» — это статус, а не акцент темы

В палитре был синий `--iw-info`: им набраны врезки уровня «информация» в
замечаниях расчётного движка (`severity: 'info'` в `CalcNote`). Это
семантический цвет статуса, а не акцент интерфейса, поэтому при перекраске в
зелёное он **не менялся** — иначе информационная врезка перестала бы
отличаться от подтверждающей.

Семантические цвета пришлось переопределить в светлой теме: значения тёмной
рассчитаны на тёмный фон, и на белом «зелёный успех» стал бы нечитаемым, а
тёмная подложка врезки — чёрным пятном. Смысл цветов при этом сохранён:
зелёный — хорошо, красный — ошибка.

## Решение 68. Приглушённый текст подобран расчётом, а не на глаз

Токен `text-dim` встречается 145 раз, в основном в подписях 12 px. По
контрастным требованиям это обычный текст, а не крупный, значит нужно 4,5:1 —
и не к фону страницы, а к самой невыгодной подложке, на которой он лежит
(`surface-3`, где им набраны чипы и кружки-счётчики).

Значения подобраны перебором до порога 4,5:1 по всем четырём поверхностям:
тёмная #8F9E95, светлая #5C6B61. После правки все текстовые роли (`text`,
`text-muted`, `text-dim`, `accent-ink`) держат AA в обеих темах, худший
случай — 4,62 в тёмной и 4,67 в светлой.

## Решение 69. Цвета SVG и графиков переведены на токены

Схемы уроков, канвас раскладки, карточки полосовых форсунок и оба графика
насосов держали цвета литералами вида `rgb(11 18 32)` — копиями значений
тёмной палитры. При второй теме они остались бы тёмными пятнами на белом.
Все они переписаны на `rgb(var(--iw-*))`: Chromium понимает `var()` в
презентационных атрибутах SVG, и Recharts передаёт цвета именно туда.

Два места так не лечатся, и оба обработаны отдельно:

1. **Выгрузка плана участка в PNG.** Сериализованный SVG рисуется как
   отдельный документ, где переменные страницы не действуют, а `fillStyle`
   холста `var()` не понимает вовсе. Появился `renderer/lib/theme.ts`:
   `themeVariablesInlineStyle()` переносит значения текущей темы в корень
   копии SVG, `themeColor()` отдаёт готовый цвет для холста. Без этого
   экспортированный план вышел бы бесцветным.
2. **Палитра кривых насосов** (`pumpCurveColors.ts`) — восемь категориальных
   цветов, включая синий. Это не хром интерфейса, а различение серий на одном
   графике: цвета зафиксированы предыдущей задачей поимённо и обязаны
   оставаться различимыми между собой, а не соответствовать теме. Оставлены
   как есть; на токен переведена только характеристика системы — она
   нейтральная линия сравнения, а не серия.

## Решение 71. Логотип подключается файлом, а не data-URL

В `content/ARTlogo.png` знак уже содержит название бренда, поэтому в шапке и
на экране выбора профиля он заменил и эмодзи капли, и текстовую надпись —
подпись рядом дублировала бы название.

Сначала картинка вшивалась в бандл как data-URL из опасения, что строгая CSP
(`img-src 'self'`) не пропустит файл при загрузке страницы по `file://`.
Проверка в собранном приложении показала, что пропускает: логотип виден и в
шапке, и на экране выбора профиля. Поэтому оставлен обычный импорт — бандл не
растёт на 650 КБ.

Знак читается на обеих темах: тёмно-зелёная плашка светлее фона тёмной темы,
светло-зелёные кроны различимы на белом. Иконка окна и панели задач берётся
из того же файла — отдельного `.ico` нет, потому что сборщик установщика в
проекте не настроен, а Electron принимает PNG напрямую.

## Решение 72. Каталог Hunter читается частями со сквозной нумерацией полос

Каталог Vol. 41 лежит в `/content` двумя файлами вместо одного:
`…-RU-1-124.pdf` (124 листа) и `…-RU-125-228.pdf` (104 листа), всего 228 полос.
Прежние цельные PDF удалены, и скрипты извлечения на них больше не запускались.

Появился `scripts/lib/hunter-catalog.mjs` — читалка по **номерам полос
издания**, а не листов внутри части. `source_page` в базе обязан указывать на
настоящую страницу каталога: ссылка «стр. 3 файла part-2» никому ничего не
говорит.

Порядок частей **не берётся из имён файлов**. Алфавитная сортировка совпала с
нужной случайно; при другом разбиении «-9-…» встал бы после «-10-…». Диапазон
объявлен явно, а при открытии сверяется с печатным номером полосы внутри
самого документа: несколько проб на часть, потому что подвала нет на титуле и
разделителях. Расхождение хотя бы на одной найденной полосе — ошибка сборки.
Проверяются также стык диапазонов без пропусков и нахлёстов и совпадение числа
листов с диапазоном.

Смещения, подтверждённые печатными полосами: часть 1 — 0, часть 2 — +124.

## Решение 75. LEO разбирается по координатам PDF, а не по плоскому тексту

Каталог LEO — сканы: 62 пробы по обеим частям дали ноль символов. Распознавание
дало два представления одного и того же: плоский текст
`LEO_Industrial_Pumps_text.txt` и PDF с текстовым слоем
`LEO_Industrial_Pumps_OCR_1.pdf`. Разбирается **PDF**.

**Почему координаты решают.** Первый заход шёл по плоскому тексту: там колонки
приходилось угадывать по порядку слов, и стоило распознаванию потерять одно
значение, как весь ряд напоров сдвигался относительно ряда расходов — строка
переставала сходиться и отбрасывалась. Из девятнадцати таблиц уцелело
37 моделей.

В PDF у каждого слова есть координата, и напор привязывается к своему столбцу
расхода по горизонтали. Пропуск в клетке остаётся пропуском в своей клетке и
не двигает соседей. Наглядный случай — `LVR(S)200-4-26`: в тексте на месте
седьмого значения стоит кириллическая «Ш», и текстовый разбор терял строку
целиком; координатный пропускает битую клетку и сохраняет остальные семь
точек.

**Итог: 193 модели из 44 таблиц на 39 полосах** — вместо 37. Отброшено
148 строк с потерянной десятичной точкой и 668 битых.

**Четыре проверки, каждая ловит свой класс ошибок:**

1. *Кривая не растёт* — перепутанные колонки.
2. *Соседние точки не отличаются больше чем впятеро* — потерянная десятичная
   точка в середине ряда, которая монотонность не нарушает.
3. *Мощность сходится с гидравлической* (P = Q · H / 367, отношение 0,8–8) —
   случай, когда в колонку мощности попал напор. Без неё в выгрузку прошли бы
   EVPm6-4 с «373 кВт» при напоре 37 м и ещё 54 такие же строки.
4. *Шаг ряда расходов регулярен* — потерянная точка **в шапке**: «2,5 2,8 3,2»
   читается как «25 28 32», ряд остаётся возрастающим, и ось расхода уезжает
   на порядок. Проверка сравнивает каждый шаг с медианным.

Строки, которые «чинятся» сдвигом десятичной точки, по-прежнему отбрасываются,
а не восстанавливаются: если испорченное число всё равно меньше предыдущего,
ошибка не обнаруживается ничем, и в справочник попадёт напор, завышенный
вдесятеро. По такому напору подберут насос.

**Остаточный риск, который не ловится ничем.** Подмена цифры, оставляющая ряд
правдоподобным: «60» вместо «64» в шапке даёт ошибку расхода в 6 %, и ни одна
из четырёх проверок её не видит. Поэтому все записи LEO помечены
`digitized = 1`, в интерфейсе они показываются с пометкой о происхождении, а в
`digitized_note` стоит номер полосы для сверки.

**Ручная сверка 30.08.2026.** Открыть сам скан не удалось — файл в 262 МБ выше
предела чтения PDF в контекст. Поэтому сверка перекрёстная: результат
координатного разбора против независимого разбора того же распознавания из
плоского текста. Четыре модели, все сошлись:

| Модель | Полоса | Координатный разбор | Тот же ряд в тексте |
|---|---|---|---|
| LVR(S)4-21 | 21 | 4→169 … 8→75, P2 4 кВт | `4 · 203 200 184 169 152 134 103 75` |

## Решение 79. Описание привязывается к ближайшей модели, а не к диапазону

Первая версия связывала строки описания с моделью по правилу «от этой модели
до следующей». Это ломалось на половине полос: код модели в каталоге то
выключен по верхней строке блока, то по центру, и тогда первая строка
описания оказывается **выше** своего кода. Получалось «ECO-MAT-16 — орошения,
моток длиной 100 м», где начало фразы уехало к предыдущему изделию.

Теперь каждая строка описания достаётся ближайшей по вертикали модели. Одно
правило покрывает обе выключки.

**Что ещё чистится при разборе:**

- **Расшифровки артикула** («= 30 м = 15 см = чёрный») — это ключ к
  обозначению, а не изделие; в перечне он выглядел бы как товар. Отбрасываются
  по признаку двух и более знаков равенства.
- **Перекрёстные ссылки** («См. стр. 183») — навигация по печатному изданию,
  а не характеристика изделия.
- **Записи без описания** — код артикула без назначения справочником не
  является.
- **Повторы**: один артикул встречается в своём разделе и в сводной таблице
  совместимости; остаётся запись с более полным описанием.

Из 287 найденных строк в справочник прошли 215.

## Решение 81. Уроки расширены разбором на числах, а не пересказом

**Дата:** 2026-08-30

Первая редакция курса объясняла принципы, но почти не показывала, как
принцип превращается в число. Уроки дополнены по единому шаблону:
заголовок → порядок действий на объекте → подстановка в формулу с готовым
результатом → таблица ориентиров → предупреждение о типовой ошибке.

Правила расширения:

- **Ни одной новой цифры «по памяти».** Все добавленные подстановки
  посчитаны из уже принятых в курсе величин (ET0, Kc, DU, влагоёмкость,
  C = 150 по Хазену–Вильямсу) и проверены расчётом перед вставкой. Пример
  гидравлики уровня 4 после проверки исправлен: hf = 2,1 м, а не 2,3 м.
- **Никаких новых каталожных значений.** Там, где нужен конкретный расход
  сопла или паспортная кривая, текст отсылает к справочнику и техкарте.
- **Ничего нового в глоссарий и калькуляторы.** Добавлялись только блоки
  текста, списков, таблиц, врезок и формул — новых ссылок `[[термин]]`,
  `calculator` и `reference` не вводилось, поэтому связность курса не
  изменилась.
- Блоки для монтажника и проектировщика помечены `audience`, чтобы
  владельцу участка не выпадали выкладки.
- Время чтения пересчитано по фактическому объёму: прежний счётчик считал
  только строковые поля верхнего уровня и занижал объём вдвое, теперь
  учитываются пункты списков и содержимое таблиц.

**Итог:** 60 уроков, 508 → 915 блоков, 92 300 → 173 127 знаков
(в среднем 1538 → 2885 знаков на урок).

## Решение 82. Калькулятор подбора насоса перестроен на порядок вопросов

**Дата:** 2026-08-30

Калькулятор §5.11 считал верно, но читался плохо. Форма была плоским списком
из четырнадцати полей, шесть из которых — точки паспортной кривой, включённые
по умолчанию: человек видел «Точка 1: расход» раньше, чем ответ на вопрос,
какой вообще нужен насос. В результате три разные величины — расчётная точка,
требуемый напор с запасом и рабочая точка — назывались вперемешку и в
подписях графика, и в плитках результата.

Перестроено по порядку вопросов, которые человек задаёт на самом деле:

1. **Из чего сложился напор.** Новая карточка разбирает требуемый напор на
   слагаемые с долями и с указанием, что с каждым можно сделать. На типовых
   данных видно, что больше половины занимает рабочее давление дождевателя,
   которое урезать нельзя, а потери на трение — 11 %.
   Слагаемые считает движок (`pumpHead().values.breakdown`), а не интерфейс:
   формул в UI по-прежнему нет.
2. **Какой насос взять.** Подбор по каталогам, ничего вводить не нужно.
3. **Что будет с этим насосом.** Проверка по паспорту — теперь необязательный
   шаг 3, выключенный по умолчанию.

Дополнительно:

- **Группы полей в форме.** Новый вид поля `section` — заголовок с пояснением.
  Расчёта не касается, из выгрузок исключён; пригодится и другим формам с
  десятком полей.
- **Три точки названы один раз** отдельной карточкой над подбором, а подписи
  на графиках приведены к этим названиям. На графике своего насоса появилась
  штриховая линия требуемого напора с запасом: она лежит выше характеристики
  системы ровно на величину запаса, и смешивать их в одной линии было бы
  неправдой — характеристика системы это физика, а запас допуск расчёта.
- **Плиток результата четыре вместо шести**: слагаемые ушли в разбор.

**Как проверить:** `npm run build && npm start` → «Калькуляторы» → §5.11.

## Решение 83. В подборе насоса добавлен нижний предел расхода

**Дата:** 2026-08-30

Проверка вживую показала дефект подбора: первой рекомендацией для садовой
системы 4 м³/ч шёл **LEO EVP6-6 — промышленный насос на 100 м³/ч и 22 кВт**.
Формально он проходил: при четырёх кубометрах в час он даёт почти свой напор
при нулевом расходе, то есть попадал и в требуемый напор, и в предел запаса
+30 %. Фактически он работал бы у самого левого края кривой — с КПД около
нуля и перегревом, о чём прямо сказано в уроке §5.11.

Причина: подбор проверял только напор. Добавлено третье условие —
`PUMP_MIN_FLOW_SHARE = 0,15`: требуемый расход должен составлять не меньше
15 % от максимального расхода паспортной кривой.

Порог откалиброван по данным: для точки 4 м³/ч × 56,8 м разумные бытовые
насосы попадают в 22–67 % своего расхода, промышленные — в 4 %. Выдача
сократилась с 17 моделей до 11, первой стала LEO EvP6-7 на 3 кВт.

Заодно ушла проблема графика: ось расхода растягивалась до 100 м³/ч ради
одной промышленной кривой. Характеристика системы дополнительно обрывается
выше полутора требуемых напоров — эта ветвь растягивала вертикальную ось до
200 м, хотя туда не дотягивается ни один подходящий насос.

**Чего сознательно не сделано:** проверки соразмерности по мощности.
Написанный было тест «мощность не больше десяти гидравлических» упал на
Speroni ECOTRI 750-T, и данные оказались верными: у пологих напорных станций
такое соотношение штатно. Подгонять порог под данные, чтобы тест позеленел,
значит выдумывать критерий — тест удалён, критерий остался один и по кривой.

**Как проверить:** `npx vitest run --root packages/core src/pump` (35 тестов)

## Решение 85. Уровень 7 «Обвязка и защита насосного агрегата»

**Дата:** 2026-08-31

Добавлен седьмой уровень Академии: тринадцать уроков об элементах, которые
стоят вокруг насоса. Десять обязательных тем задачи (обратные клапаны,
запорная арматура, манометры, прессконтроль, реле давления, пускатели,
частотники, гидроаккумуляторы, датчики сухого хода, защита обратного потока)
плюс три дополнительных: механическая защита (грязевик и компенсатор),
предохранительный клапан с байпасом и итоговый урок «Обвязка целиком».

**Схемы рисует один параметризованный чертёж, а не тринадцать картинок.**
`shared/pump-rig-figures.ts` описывает состав каждой схемы данными, а
`PumpRigFigure.tsx` рисует их одним и тем же чертежом: источник слева, насос
в середине, система справа, электрическая часть сверху пунктиром. Ученик,
перейдя к следующему уроку, узнаёт ту же схему и видит на ней только новый
элемент — ради этого схемы и делались общими. Состав вынесен в `shared`,
потому что его читает и тест наполнения Академии: перечень нарисованных схем,
переписанный в тесте руками, разошёлся бы при первом же добавлении урока.

**Содержание качественное намеренно.** Числовых характеристик конкретных
изделий в уроках нет: потери на обратном клапане, уставки реле, объём бака и
давление воздуха берутся из паспорта оборудования, а не из учебника (§10 п.2).
Расчётные вопросы по уровню считает движок — см. решение 86.

**Схема базы.** Перечень уровней зашит в `CHECK`, а `CHECK` в SQLite меняется
только пересборкой таблицы. Миграция V10 делает это по документированному
порядку с `legacy_alter_table` на время переименования: между `DROP` и
`RENAME` ссылка `questions.lesson_id → lessons` временно висит в пустоту, и
в современном режиме переименование падало бы. Миграция проверена на копии
рабочей базы: 60 уроков перенесены, битых ссылок нет, `integrity_check` — ok,
`CHECK` по-прежнему ловит опечатку в названии уровня.

**Как проверить:** «Академия» → «Уровень 7».

## Решение 87. Тренажёр «Сборка узла насоса»

**Дата:** 2026-08-31

Новый раздел: обвязка разложена на позиции — несколько на всасе, несколько на
напоре, — и в каждую надо поставить элемент из палитры. Три задания: базовая
обвязка поверхностного насоса, гидрофорная установка и подключение к
городскому водопроводу с фертигацией.

**Расстановка сделана выбором, а не перетаскиванием.** Позиции здесь заданы
схемой, и перетаскивание не добавляет ничего, кроме требования к точности
мыши: оно не работает с клавиатуры и хуже на небольших экранах. Выбор двумя
щелчками — позиция, затем элемент — делает то же самое; фокус после установки
сам переходит к следующей пустой позиции, поэтому узел собирается подряд.

**Обратная связь по каждой ошибке — то, ради чего тренажёр и нужен.** В разборе
позиции сказано, что там должно стоять и почему, а к этому добавлено
пояснение того элемента, который поставили: «Манометр на напоре ставят между
насосом и обратным клапаном. За клапаном он показывает давление системы, а не
насоса». Пояснения `misplaced` лежат у элементов, а не в парах «позиция ×
элемент»: пар было бы под сотню на задание, и половина осталась бы без текста.

**Эталон не уходит в интерфейс до проверки** — как в «Найди ошибку». Тест это
проверяет буквально: в сериализованном ответе `assembly:task` не должно быть
ни `correct`, ни `why`, ни `misplaced`.

**Проверку считает движок:** `scoreAssembly` в `packages/core`, там же
юнит-тесты. Один и тот же элемент законно стоит в нескольких позициях (кран),
поэтому сверяется каждая позиция со своим эталоном, а не набор с набором.

**Тест поймал слабое задание:** в первом задании было шесть элементов на шесть
позиций, и оно решалось методом исключения. Правило сформулировано точнее — в
палитре должен быть элемент, которого в эталоне нет вовсе, — и в задание
добавлены два таких.

**Как проверить:** «Сборка узла насоса» → любое задание → «Проверить сборку».

## Решение 89. Установщик для Windows

**Дата:** 2026-08-31

Собран NSIS-установщик через electron-builder: `npm run dist` →
`release/ArtLandshaft-Setup-0.1.0.exe`, 107 МБ.

**Что попадает в дистрибутив.** В `/content` лежит 365 МБ исходников для
скриптов извлечения — каталоги Hunter, Speroni, LEO, Grundfos. Приложению они
не нужны: оно читает только собранные JSON. Поэтому `extraResources` берёт из
`/content` по маске `**/*.json` и логотип — 3,4 МБ вместо 365.

**node_modules в пакет не кладутся вовсе.** main и preload собраны esbuild,
renderer — Vite; из внешнего в бандле остаются только `electron` и
`node:sqlite`, которые даёт рантайм. Проверено по самому бандлу: других
`require` в нём нет. Итог — `app.asar` весит 1,75 МБ, а не тянет за собой весь
монорепозиторий вместе с pdfjs и самим electron-builder.

**Имена: латиница в файлах, кириллица на виду.** Первая сборка поставила
программу в каталог `@irrigoelectron-app`: сборщик вычищает из `productName`
всё, что не годится для пути, и от «АртЛандшафт» не остаётся ничего, после чего
он берёт имя пакета. Поэтому `productName` и `executableName` — `ArtLandshaft`,
а пользователю везде видно «АртЛандшафт»: ярлык на рабочем столе и в меню
«Пуск», заголовок окна, название внутри программы. Издатель — из поля `author`,
иначе Windows показывает пустую строку.

**Установка в профиль пользователя** (`perMachine: false`): не требует прав
администратора и не упирается в политику Application Control, из-за которой в
этом проекте нет ни одного нативного модуля (решение 1). Диалог с выбором
каталога оставлен: на целевых машинах системный диск часто маленький.

**Прогресс переживает переустановку.** `deleteAppDataOnUninstall: false`, а база
лежит в `userData`. Имя каталога данных осталось прежним — `IrrigoMaster`
(`app.setName` в main): переименование в «АртЛандшафт» осиротило бы уже
существующую базу с пройденными уроками, а видимой пользы не даёт.

**Иконка собирается из логотипа своим скриптом** `scripts/build-app-icon.ts`:
PNG распаковывается штатным zlib, знак обрезается по прозрачным полям,
усредняющим фильтром вписывается в квадрат 512×512, из которого
electron-builder делает `.ico`. Нативный `sharp` в этом проекте недопустим,
а тянуть jimp ради одной операции незачем.

**Проверено на машине:** тихая установка (`/S`) → каталог
`%LOCALAPPDATA%\Programs\ArtLandshaft`, ярлыки на месте, программа
запускается. Отдельно проверен первый запуск «с нуля» — с чистым каталогом
профиля (`--user-data-dir`), чтобы не трогать данные пользователя: база
создалась и наполнилась из упакованного контента (73 урока, 422 вопроса, 512
насосов, 1254 сопла). Деинсталлятор проверен на первой сборке — удалил всё.

**Чего в установщике нет: подписи.** Сертификата у проекта нет, поэтому
SmartScreen при первом запуске покажет предупреждение «Windows защитила ваш
компьютер» — это ожидаемо для неподписанного установщика, а не признак
неисправности. Подпись потребует покупки сертификата; в конфигурацию она
добавляется полем `win.certificateFile`.

## Решение 90. Android-сборка: одна кодовая база, подмена трёх узловых модулей

**Дата:** 2026-09-01

Приложение выпущено под Android: `packages/mobile-app` — оболочка Capacitor,
`npm run android:apk` → `release/ArtLandshaft-0.1.0-android-debug.apk`, 7,7 МБ.
Схема повторяет WELD MASTER, но упирается в другое ограничение: там прикладной
слой изначально лежал в `core` и мобильный мост просто звал сервис, а здесь вся
работа с базой живёт в `packages/electron-app/src/main/db` и написана под
синхронный `DatabaseSync` из `node:sqlite` (решение 1).

**Второй реализации нет — есть три алиаса.** Вместо переписывания слоя базы под
браузер мобильный `vite.config.ts` подменяет ровно те узловые модули, которые
этот слой использует:

| модуль | чем заменён | почему так |
| --- | --- | --- |
| `node:sqlite` | `src/platform/node-sqlite.ts` — API `DatabaseSync` поверх sql.js | sql.js синхронен, как и `node:sqlite`; асинхронный драйвер (нативный плагин SQLite) заставил бы переписать на промисы каждый запрос, каждую транзакцию и всю прикладную логику — то есть содержать вторую копию правил |
| `node:fs` | `src/platform/node-fs.ts` — чтение вшитого в бандл `/content` | у страницы в WebView файловой системы нет, а наполнению нужны ровно `existsSync`, `readFileSync`, `readdirSync` |
| `node:path` | `src/platform/node-path.ts` — `dirname`/`join` поверх «/» | настоящих путей в мобильной сборке нет, есть виртуальные к контенту |

Благодаря этому `src/main/db/**` (схема, миграции, десять модулей наполнения,
тринадцать репозиториев) попадает в APK **без единой правки**, а расчётный
движок `@irrigo/core` — тем более. Экраны renderer тоже переиспользованы
целиком: мобильный пакет не содержит ни одного собственного экрана.

**Граница «оболочка/приложение» вынесена в `PlatformServices`.** Прежний
`ipc/register.ts` смешивал обработчики каналов с вызовами Electron (диалоги
сохранения, буфер обмена, версии среды). Он разделён: `ipc/handlers.ts` —
`createHandlers(db, platform)`, общий на обе платформы; `ipc/register.ts` —
тонкая обвязка `ipcMain`; `packages/mobile-app/src/bridge.ts` — тот же
`createHandlers`, только `window.irrigo` ставит сама страница, потому что в
WebView двух процессов нет и разделять нечего. Поле `AppInfo.electronVersion`
и `nodeVersion` заменены на `runtime` и `platform`: под Android первое
бессмысленно.

**Что пришлось сделать иначе, чем на десктопе.**

- *База живёт в памяти и сохраняется вручную.* sql.js держит SQLite в
  WebAssembly, поэтому после каждой изменяющей операции образ выгружается в
  приватный файл приложения (`Directory.Data`, плагин Filesystem). Запись
  отложена на 500 мс — одно действие пользователя это несколько операций
  подряд — и форсируется при сворачивании (`App.pause`) и при уходе страницы.
  Хук `onMutate` в `PlatformServices` вызывается только у каналов, меняющих
  базу; список задан явно, а не «на всякий случай после каждого вызова».
- *Кэш подготовленных запросов.* Репозитории зовут `db.prepare(...)` на каждый
  запрос и не освобождают результат: под `node:sqlite` за этим следит сборщик
  мусора, а забытый `Statement` в sql.js навсегда занимает память
  WebAssembly. Адаптер кэширует запросы по тексту SQL — это заодно ускорило
  наполнение (тысячи вставок в цикле).
- *`export()` в sql.js освобождает все подготовленные запросы* и переоткрывает
  соединение. Кэш после него указывает в никуда, и следующий же запрос падает
  с «Statement closed» — что и произошло при первой проверке в браузере.
  Поэтому выгрузка образа идёт через `DatabaseSync.export()`, который сначала
  сбрасывает кэш.
- *Экспорт файлов — через «Поделиться».* Системного диалога «Сохранить как» в
  WebView нет, а во внешние папки Android до 10-й версии пускает только по
  разрешению. CSV расчёта и PNG плана пишутся в приватный кэш и отдаются в
  системное меню обмена.
- *Аппаратная кнопка «назад».* Без обработчика она закрывает приложение из
  любого места. Порядок: закрыть верхнее наложение (стек в
  `renderer/lib/overlay.ts`), иначе шаг назад по разделам, иначе выход с
  принудительным сохранением базы.

**Контент вшит в бандл.** 25 JSON-файлов `/content` (2,9 МБ) попадают в бандл
текстом через `import.meta.glob(..., '?raw')` — текстом, а не разобранным
объектом, чтобы подпись контента считалась ровно так же, как на десктопе. APK
неизменяем, папки приложения у пользователя нет: правится `/content`,
пересобирается APK. Итоговый бандл — 3,4 МБ JS плюс 0,7 МБ sql-wasm.

**Тренажёр раскладки переведён на события указателя.** `LayoutCanvas` слушал
только мышь, а на телефоне перетаскивание пальцем не порождает `mousemove`
вовсе: браузер шлёт `touchmove`, а мышиные события подставляет уже по
окончании касания. Постановка головы тапом работала бы, перетаскивание — нет.
Теперь это `onPointerDown/Move/Up`, один код на мышь, палец и стилус, с
захватом указателя на голове (палец почти всегда сходит с кружка радиусом
0,35 м) и `touch-action: none` у рабочего канваса — иначе браузер счёл бы
протяжку прокруткой страницы и увёл бы голову из-под пальца. В режиме
просмотра прокрутка не отбирается.

**Интерфейс адаптирован, а не продублирован.** `Shell.tsx` стал отзывчивым: от
ширины `lg` меню стоит на месте, ниже — выезжает поверх содержимого по кнопке
(256 px постоянного меню на экране 360 px не оставили бы места уроку). Добавлены
кнопка поиска (Ctrl+F на телефоне нет), отступы под системные полосы через
`env(safe-area-inset-*)`, увеличенная высота пунктов меню под палец. В
мобильном `styles.css` — запрет резиновой прокрутки страницы целиком, размер
поля ввода 16 px (меньший прошивки увеличивают масштабом при фокусе, и страница
остаётся зумленной) и горизонтальная прокрутка широких таблиц справочников.
Настольная вёрстка не изменилась: минимальная ширина окна там 1100 px.

**Проверка.** Юнит-тесты `packages/mobile-app/test/android-db.test.ts` (14
проверок) прогоняют настоящее наполнение из `/content` через SQLite в
WebAssembly и все ключевые репозитории, включая круг «выгрузить образ →
переоткрыть → данные на месте». Сверх того собранный бандл — тот самый, что
лежит в APK — поднят в headless Chrome по протоколу DevTools: старт 2,1 с,
ошибок страницы нет, справочники собрались (1254 сопла, 512 насосов, 4100 точек
кривых, 422 вопроса, 73 урока), билет экзамена 60 вопросов с долей расчётных
52 %, подбор насосов даёт 22 совпадения; повторный запуск переиспользует
сохранённую базу. Отдельно проверены касания: с включённой эмуляцией тач-ввода
(`Input.dispatchTouchEvent`, без синтетической мыши) в тренажёре раскладки
дождеватель ставится тапом и перетаскивается пальцем, покрытие и замечания
пересчитываются на лету. Эмулятора Android на машине нет, поэтому проверка на
самом устройстве остаётся за пользователем; движок WebView — тот же Chromium.

**Разрешение INTERNET оставлено в манифесте** (как и в WELD MASTER): его просит
шаблон Capacitor, а локальный сервер WebView без него на части прошивок не
поднимается. Офлайн-обещание §13 держится не разрешением, а тем, что в коде нет
ни одного сетевого вызова, и CSP в `index.html` запрещает любые внешние
источники (`default-src 'self'`).

**Сборка требует JDK 17–24.** Gradle 8.14 не запускается на JDK 25, который
несёт нынешняя Android Studio, и падает с невнятным «Unsupported class file
major version 69». Поэтому `scripts/build-android-apk.ts` сам ищет подходящий
JDK (`JAVA_HOME`, `~/.jdks`, `Program Files/Java`, jbr Android Studio) и
подставляет его; на машине разработчика для этого положен Temurin 21 в
`~/.jdks`. Скрипт делает всё разом: бандл → иконки → `cap sync` → gradle →
копия в `release/`.

**Иконки и заставка** генерируются из того же `content/ARTlogo.png`, что и
иконка Windows: кодек PNG вынесен из `build-app-icon.ts` в общий
`scripts/lib/png.ts`, а `build-android-icons.ts` делает набор mipmap (обычная,
круглая с маской, слой адаптивной иконки с полем под 66 dp безопасной зоны) и
заставки под пять плотностей в двух ориентациях.

**Подпись.** Debug-APK подписан отладочным ключом и ставится на устройство
сразу. Релизный собирается только при наличии ключа —
`android/keystore.properties` (в `.gitignore`) или переменные
`ANDROID_KEYSTORE_*`; так же устроен и workflow `.github/workflows/build-android.yml`.
